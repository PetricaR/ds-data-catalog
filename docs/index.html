DS Data Catalog

A self-hosted data catalog for Google Cloud / BigQuery teams. Discover, document, govern, and monitor your data assets — with AI-powered insights, PII detection, quality scans, and lineage.

FastAPI + React 18 BigQuery Native Vertex AI Gemini GKE Autopilot Google OAuth2 Cloud DLP Dataplex Asset Inventory

Overview

DS Data Catalog is a FastAPI + React application that runs on GKE Autopilot. It connects to your BigQuery projects, syncs table and column metadata, and gives your team a searchable, documented, trusted view of your data assets — entirely within your own GCP project.

Architecture

All traffic flows through a single LoadBalancer IP. The frontend nginx container proxies /api/v1/ to the backend — no separate backend ingress is needed.

Features

🔍

Data Discovery

Browse all BigQuery datasets and tables in a tree view. Full-text search across names, descriptions, columns, and tags. Filter by sensitivity, owner, dataset.

📝

Table Documentation

Inline-editable table and column descriptions. Sensitivity labels, custom tags, owner assignment, and example SQL queries per table.

✅

Trust Certification

Validate and certify tables and specific columns. Dedicated Trusted Data page. Google Chat notifications on trust changes.

🔄

Schema Change Detection

Automatic detection of columns added or removed on every BQ sync. Visual diff alerts with acknowledge-and-dismiss workflow.

👁️

Data Preview

TABLESAMPLE query with cost estimate before execution. Run inline and save to example queries.

🤖

AI Insights

Gemini-generated analysis questions, observations, and ML use cases based on schema and stats. Regeneratable on demand.

🔗

Data Lineage

Manual upstream/downstream table references. Auto-discovery via Cloud Data Lineage API. Merges both sources.

🛡️

PII Detection

Cloud DLP async inspection of BigQuery tables. Auto-flags columns containing PII. Per-column is_pii toggle.

📊

Quality Scans

Dataplex DataScans for managed quality checks. Per-table scores and dimension breakdowns (completeness, validity, etc.).

📈

Usage Statistics

Query frequency and top users from BigQuery INFORMATION_SCHEMA.JOBS. Last-queried timestamp per table.

🕐

Schema History

Column additions, removals, and type changes via Cloud Asset Inventory. Up to 30 days lookback.

🔔

Notifications

In-app notification feed. Google Chat Cards v2 webhooks for trust events, metadata changes, PII findings, and quality scores.

🔄

Multi-Source Sync

Register multiple GCP projects as sync sources. Per-source service account key via Secret Manager or Workload Identity.

🎫

DS Project Tracking

Link tables to JIRA tickets and GitHub repos. Track which internal projects depend on which tables.

Prerequisites

Local Development

  • Python 3.12+
  • Node.js 20+
  • PostgreSQL 16 (local or Docker)
  • gcloud CLI authenticated (gcloud auth application-default login)

Production (GKE)

  • GCP project with billing enabled
  • gcloud CLI authenticated with Owner or Editor role
  • kubectl
  • gke-gcloud-auth-plugin (gcloud components install gke-gcloud-auth-plugin)
  • docker — only needed if not using Cloud Build (Cloud Build is the default)

Backend Setup (Local)

Create virtual environment & install dependencies

# From repo root
cd catalog_app
python3 -m venv catalog_env
source catalog_env/bin/activate

pip install -r requirements.txt

Create local database

createdb ds_catalog
psql ds_catalog -c "CREATE USER catalog WITH PASSWORD 'catalog';"
psql ds_catalog -c "GRANT ALL PRIVILEGES ON DATABASE ds_catalog TO catalog;"

Create .env file

# catalog_app/.env
DATABASE_URL=postgresql://catalog:catalog@localhost:5432/ds_catalog
GCP_PROJECT_ID=your-project-id
GOOGLE_CLIENT_ID=your-oauth-client-id
GOOGLE_CLIENT_SECRET=your-oauth-client-secret
FRONTEND_URL=http://localhost:5173
JWT_SECRET=local-dev-secret
SECRET_KEY=local-dev-secret
CORS_ORIGINS=["http://localhost:5173"]

Run the backend

uvicorn backend.main:app --reload --port 8000

The server auto-creates all database tables via SQLAlchemy on startup. API is available at http://localhost:8000. Interactive docs at http://localhost:8000/docs.

Frontend Setup (Local)

Install dependencies

cd catalog_app/frontend
npm install

Start dev server

npm run dev

Vite starts at http://localhost:5173. API calls to /api/v1/* are proxied to http://localhost:8000 via the Vite proxy already configured in vite.config.ts. No .env.local needed.

Stale HMR cache: If UI changes don't appear after code edits, kill the dev server, run rm -rf node_modules/.vite, and restart with npm run dev.

Step 3 — Secret Manager Secrets

The deploy script reads all secrets from Secret Manager automatically. Create them once:

PROJECT_ID=your-project-id

# Google OAuth2
echo -n "your-google-client-id" | \
  gcloud secrets create GOOGLE_CLIENT_ID --data-file=- --project=$PROJECT_ID

echo -n "your-google-client-secret" | \
  gcloud secrets create GOOGLE_CLIENT_SECRET --data-file=- --project=$PROJECT_ID

# JWT signing secret (strong random string)
echo -n "$(openssl rand -hex 32)" | \
  gcloud secrets create jwt-secret-key --data-file=- --project=$PROJECT_ID

# Gemini API key (optional — uses Vertex AI via Workload Identity if empty)
echo -n "your-gemini-api-key" | \
  gcloud secrets create gemini-api-key --data-file=- --project=$PROJECT_ID

# Google Chat webhook (optional)
echo -n "https://chat.googleapis.com/v1/spaces/SPACE_ID/messages?key=..." | \
  gcloud secrets create ds-catalog-google-chat-webhook --data-file=- --project=$PROJECT_ID

Step 6 — Deploy the Application

cd catalog_app/deploy

# Full deploy (handles everything)
GCP_PROJECT_ID=your-project-id \
GCP_REGION=europe-west1 \
CLUSTER_NAME=ds-catalog-cluster \
  ./deploy.sh

# If cluster already exists, skip creation
GCP_PROJECT_ID=your-project-id \
GCP_REGION=europe-west1 \
CLUSTER_NAME=ds-catalog-cluster \
SKIP_CLUSTER=1 \
  ./deploy.sh

The script will:

  1. Check prerequisites (gcloud, docker, kubectl)
  2. Enable GCP APIs
  3. Create or reuse the GKE cluster
  4. Set up Workload Identity
  5. Build backend and frontend images via Cloud Build (no local Docker needed)
  6. Apply Kubernetes manifests: PostgreSQL StatefulSet, ConfigMap, Secrets, ServiceAccount, Deployments, Services, HPA
  7. Pull all secrets from Secret Manager and create the K8s secret
  8. Wait for rollouts to complete
  9. Auto-patch the ConfigMap with the real LoadBalancer IP
  10. Print the app URL

Re-deploying after code changes

Build both images and do a rolling update:

# Build new images via Cloud Build
gcloud builds submit catalog_app/ --project=your-project \
  --config=<(cat <<'EOF'

# Rolling restart — picks up :latest tag

kubectl rollout status  deployment/ds-catalog-backend  -n default --timeout=5m

After deploy, the script prints the app URL (e.g. http://34.90.12.55.nip.io). Go back to Google Cloud Console → APIs & Services → Credentials → your OAuth client and add:

  • Authorised redirect URIs: http://34.90.12.55.nip.io/api/v1/auth/callback

BigQuery Sync

The sync engine reads all datasets and tables from a GCP project and upserts them into the catalog database.

What gets synced

  • Datasets (ID, description, labels)
  • Tables (ID, description, row count, size, partition info)
  • Columns (name, type, description from BigQuery schema)
  • Schema changes — if columns were added or removed since the last sync, a schema change alert is created

Authentication

Sync uses one of two methods per source:

  • Workload Identity (default) — the pod's GCP SA is used. Works for the same project as the cluster.
  • Service account key — store the JSON key in Secret Manager, set BQ_SECRET_NAME to the secret's name. Required for cross-project sources.

Trigger

# Sync all registered sources
curl -X POST http://104.155.73.77/api/v1/bq/sync/all \
  -H "Authorization: Bearer <jwt>"

# Sync a specific project
curl -X POST http://104.155.73.77/api/v1/bq/sync \
  -H "Authorization: Bearer <jwt>" \
  -d '{"project_id":"my-project"}'

PII Detection (Cloud DLP)

Runs an asynchronous Cloud DLP inspection job against the BigQuery table and auto-flags columns that contain PII.

How it works

  1. Backend calls dlp.create_dlp_job() with the BigQuery table reference
  2. Polls the job until status is DONE (typically 30–120 seconds)
  3. Calls dlp.list_findings() to get per-column PII results
  4. Automatically sets is_pii = True on columns that had findings
  5. Sends a Google Chat notification with the PII summary

Info types detected

The DLP job uses Google's built-in info types. Common findings include: EMAIL_ADDRESS PHONE_NUMBER PERSON_NAME CREDIT_CARD_NUMBER US_SOCIAL_SECURITY_NUMBER IP_ADDRESS IBAN_CODE

Cost: DLP charges per GB inspected. For large tables, the scan can be expensive. Use the sensitivity label and column filters in DLP to limit scope if needed.

Quality Scans (Dataplex DataScans)

Creates a managed Dataplex DataScan for the table and runs it on demand. Results include a per-dimension quality score.

How it works

  1. Backend calls dataplex.create_data_scan() — idempotent (reuses an existing scan if one exists for that table)
  2. Triggers a scan run via run_data_scan()
  3. Polls the scan job until state is SUCCEEDED
  4. Returns per-rule and per-dimension results
  5. Sends a Google Chat notification with the overall score

Default quality rule

# Table-level completeness check
rule: TableConditionExpectation
sql_expression: "COUNT(*) > 0"
dimension: COMPLETENESS

Additional per-column rules (null checks, uniqueness) can be added by extending backend/services/dataplex_quality.py.

Data Lineage

Lineage is tracked in two ways that are merged into a single view:

Manual lineage

Any user can add upstream or downstream table references in project.dataset.table format via the table detail page. Stored in the catalog database.

Auto-discovery (Cloud Data Lineage API)

Clicking Auto-discover calls the Cloud Data Lineage API to find tables that this table reads from or writes to, based on BigQuery job history. Results are merged with manually entered references — no duplicates.

Requirement: The Cloud Data Lineage API must be enabled in your project, and BigQuery jobs must have been running for at least 24 hours before lineage data is available.

Schema History (Cloud Asset Inventory)

Fetches the history of BigQuery table asset snapshots from Cloud Asset Inventory and diffs consecutive snapshots to identify column-level changes.

Change types detected

  • COLUMN_ADDED — a column present in snapshot N+1 but not in snapshot N
  • COLUMN_REMOVED — a column present in snapshot N but missing in snapshot N+1
  • TYPE_CHANGED — same column name, different BigQuery type

Limits

  • Maximum lookback: 30 days (Cloud Asset Inventory retains data for 35 days; the API boundary is ~30 days from now)
  • Asset Inventory snapshots are created on every BigQuery schema change, not on a fixed schedule
# Fetch last 30 days of schema changes
GET /api/v1/tables/{id}/schema-history?days=30

Troubleshooting

Login redirects to wrong URL

The OAuth2 redirect URI in the Google Console must exactly match FRONTEND_URL + /api/v1/auth/callback. Check ConfigMap:

kubectl get configmap ds-catalog-config -n default -o yaml | grep FRONTEND

PII / Dataplex / Asset Inventory import errors

Verify all three packages are installed in the backend image:

kubectl exec -it deployment/ds-catalog-backend -n default -- \
  python -c "from google.cloud import dlp_v2, dataplex_v1, asset_v1; print('OK')"

DLP scan fails with "BQ table not found"

The DLP job runs in the GCP project set in GCP_PROJECT_ID. The BigQuery table must be in the same project, or the DLP SA must have bigquery.dataViewer on the source project.

Schema history — "Requested time must be later than..."

This means the days parameter exceeds the Asset Inventory retention window (~30 days from now). The API enforces a minimum start time of ~35 days ago. The default is 30 days — do not set days > 30.

Dataplex scan — "NonNullExpectation requires non-empty column name"

Column-level DQ rules require a column field. Use TableConditionExpectation for table-level rules (no column required). Already fixed in current version.

Frontend shows blank screen

  1. Check browser console for JavaScript errors
  2. Check that the API is reachable: curl http://<ip>/api/v1/health
  3. Clear Vite cache (local dev): rm -rf node_modules/.vite && npm run dev
  4. If an API call returns a FastAPI 422 with detail as an array, the frontend error renderer must handle non-string detail — check error display components

Backend pod in CrashLoopBackOff

kubectl logs deployment/ds-catalog-backend -n default --previous

Common causes: missing required environment variable, database not ready, PostgreSQL password mismatch.

Adapting for Your Organization

Rename from "DS Data Catalog"

Update the following files:

  • catalog_app/frontend/src/ — search for DS Data Catalog in page titles and the nav header
  • catalog_app/deploy/deploy.sh — APP_NAME variable and cluster name defaults
  • catalog_app/deploy/configmap.yaml — ConfigMap name and labels
  • K8s deployment/service YAML files — label selectors and resource names

Add a new GCP project as a BigQuery source

  1. Go to Sources in the app → Add Source
  2. Enter the GCP project ID
  3. If using a service account key: store the JSON key in Secret Manager, enter the secret name
  4. Click Sync Now

Restrict access by Google Workspace domain

The backend accepts any Google OAuth2 user by default. To restrict to your org domain, add a check in backend/api/auth.py after the OAuth callback:

if not user_info["email"].endswith("@yourcompany.com"):
    raise HTTPException(status_code=403, detail="Access restricted to company accounts")

Sensitivity labels

The four built-in sensitivity labels are: public internal confidential restricted. To add or rename them, update the enum in backend/schemas/catalog.py and the frontend select in frontend/src/pages/TableDetail.tsx.
